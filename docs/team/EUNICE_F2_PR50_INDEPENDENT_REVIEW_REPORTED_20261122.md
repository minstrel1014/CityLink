## 3. F2-M1 evidence

Mechanism in the source. `client/src/lib/appBuildMarker.ts:132` declares `let memoizedDefaultProbe: Promise<AppBuildFreshness> | null = null;` at module scope. `probeAppBuildFreshness` (lines 141-150) computes `usesDefaults = options.fetch === undefined && options.loaded === undefined`, returns the stored promise if present (line 146) and otherwise stores the **promise** before it settles (line 148). Only `resetAppBuildFreshnessProbe()` (line 163-165) clears it, and it is documented at line 162 as "Test seam only: the production code path has one freshness answer per load". `client/src/lib/supabaseGroups.ts:895` calls the **no-argument** form inside `createGroupAndInvite`, i.e. exactly the memoized path.

This matches the coordinator's two reproduced observations in substance and mechanism. Disclosure of my own method correction: my **first** harness run executed all four scenarios inside one module instance, so scenarios 2-4 inherited the first cached verdict and reported 0 additional fetches. That accidental result is itself corroborating evidence of lifetime memoization, but it is not a valid per-scenario measurement, so I re-ran with isolated instances before forming this verdict.

Why it matters, and how far it reaches. The failure needs at least two create attempts in one browser tab with a deployment landing between them. That is precisely the announced maintenance-window case the cutover plan describes: a user who already attempted a create, keeps the tab open across the Test-only window, then tries again later. After the first attempt the module never re-reads the marker again in that load, so an actually stale bundle dispatches its four-argument create instead of showing the approved message, and any marker problem that first looked `unknown` also freezes. What is **not** affected: capacity enforcement, admission authority, the old three-argument stub, the 2-19 validation order, or the exact message. Same-tab sign-out/sign-in also does not re-evaluate the marker (same root cause; not a security consequence, because the marker is build evidence, not auth state).

**F2-M2 (additional, definite, same defect family).** Because the memoized value is the promise itself and no timeout exists, an unsettled `/version.json` request pins every later default probe to the same never-settling promise. `createGroupAndInvite` awaits it before dispatch, so that attempt hangs, and in `client/src/pages/citylink/GroupWorkflows.tsx` the `actionBusy` single-flight flag (line 408, set at 422, cleared only at 447 in `finally`) stays set, which silently blocks every subsequent group action in that tab. It fails closed — no dispatch, no bypass — so this is an availability defect, not a security one. Practical likelihood is low because browsers normally settle or abort a fetch, so I record it as a lower-severity consequence of the same design rather than as a separate blocker of equal weight. Note honestly that the proposed repair in §8 does **not** by itself remove this residual, and the review packet forbids timers, so closing it needs one explicit Adam word.

## 8. Smallest owner repair recommendation (review proposal only — I made no edit)

I validated the shape in `/tmp` only, by copying the module and clearing the entry on settle: the later-deployment scenario then returned `stale` on the second probe (two fetches), the `unknown`-then-recovery scenario returned `stale`, and concurrency still issued one request. The repository was never touched; that prototype is review scaffolding, not a patch to apply.
